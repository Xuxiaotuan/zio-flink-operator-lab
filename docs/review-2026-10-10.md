# 当前版本锐评与优化计划

基线：`main @ c3fe7d4`，本轮继续优化后待提交。

## 锐评

这个项目已经从“能调用 Flink Operator”进入“有生命周期、有证据、有多副本状态来源的 HTTP 控制面”阶段。HTTP、Kubernetes Operation CR、资源观察、版本校验、快照策略和前端状态展示已经形成闭环；真实集群已经验证两副本、跨节点访问和 Kubernetes 状态统一来源。

当前最大的价值是把提交意图、Operator 处理和最终观测结果分开记录。当前最大的风险也在这里：控制面不能因为收到了请求就宣布成功，不能因为 API Server 返回 4xx 就把结果写成未知，也不能因为浏览器轮询异常而留下无提示的失败。

本轮发现并修复了三个直接影响可靠性的缺口：

1. 竞争副本先获得 `FlinkOperationLock` 再重新读取 Operation；没有租约的副本不会把共享操作误写成失败。
2. Kubernetes Operation CR 遇到 `409 resourceVersion` 冲突会重新读取并有限重试，避免覆盖另一副本刚写入的审计事件。
3. 进程在 `ValidationPassed` 之后、`Submitted` 回执之前重启时会进入 `UNCERTAIN`，拒绝再次 apply 可能已经生效的有状态操作。
4. 过期锁接管同时使用 UID 和 resourceVersion 删除前置条件，锁在读取后被续租或替换时放弃接管。
5. Operator 已明确返回的 CR `status.error` 优先于 generation 诊断，避免把真实拒绝原因隐藏成次级校验错误。
6. Kubernetes 明确返回的 4xx 是确定失败；只有网络中断、限流和 5xx 仍保留 `UNCERTAIN`，避免把权限或参数错误误报成未知结果。
6. 前端操作轮询的单次请求失败现在会被捕获并显示，轮询按钮也会在 `finally` 中恢复，避免未处理 Promise 异常和页面卡死。

## 已完成的最小计划

| 优先级 | 工作 | 验收证据 |
| --- | --- | --- |
| P0 | 竞争副本不误写 Operation | 锁竞争回归测试确认落败副本保持 `ACCEPTED` |
| P0 | Operation CR 冲突重读 | 409 回归测试确认保留并发审计事件并用新 resourceVersion 重试 |
| P0 | 提交回执缺失不重复 apply | 重启窗口测试确认写副作用次数为 0、结果为 `UNCERTAIN` |
| P0 | 锁接管带双重前置条件 | UID/resourceVersion 冲突测试确认不会误删更新后的锁 |
| P0 | 保留 Operator 确定错误 | 回归测试确认 `status.error` 不被 generation 错误覆盖 |
| P1 | 收紧提交错误语义和前端异常 | 403、Node 测试和脚本检查通过 |
| P1 | 保留可审计的评审结论 | 本文记录基线、改动、证据和剩余边界 |

## 后续计划

下一阶段只做能提升控制面可信度的工作，不扩展成通用平台：

1. 为 Kubernetes Operation Store 增加基于 `resourceVersion` 冲突的有限重读重试，并把并发推进结果记录为可解释事件。
2. 增加控制面重启后的真实接管演练，验证启动扫描、租约和重复投递在两副本下仍只产生一次资源副作用。
3. 为 VerificationEngine 补充按 Flink/Operator 版本固定的状态证据契约，尤其是 savepoint 路径、checkpoint 时间线和 fallback 语义。
4. 对真实集群增加有界压力与稳定性基线，记录吞吐、P95 延迟、API Server 错误率、操作积压和恢复时间。

这些项目完成前，不能把当前版本表述为“已经证明所有故障场景下都安全”。当前版本可以准确表述为：**HTTP-only、Kubernetes API、Kubernetes CR 统一状态、两副本可运行，并具备可测试的操作生命周期和证据验证。**

## 本轮边界

本轮修改跨副本锁竞争、Operation CR 冲突重试、提交回执缺失保护、锁接管删除条件、前端轮询错误处理和评审文档；没有改变 API 路径、状态后端选择、Flink 作业模板或集群资源。目标集群仍运行之前的 build #33，当前代码需要重新走 Pipeline 后再做现场验证。
